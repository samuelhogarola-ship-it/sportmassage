# Coolify deployment for Sport Massage Blogger

The deployment has two containers on one Compose resource:

- `blogger` runs Node, builds releases, and is the only service allowed to write content or state.
- `proxy` runs unprivileged Nginx, serves the active public release, and forwards dynamic routes to `blogger:8787`.

Neither service publishes a host port and no ingress labels target Blogger. Attach `https://sportmassagefuengirola.com` only to the `proxy` service on container port `8080`. Both services keep the internal `blogger_internal` network for proxy-to-Node traffic. Blogger also joins the non-internal `web` network so it can exchange one-time codes with the HTTPS Studio endpoint; this network provides egress but does not publish port `8787` on the host. On a VPS without Coolify, connect the existing TLS reverse proxy to `web` and route it only to `proxy:8080`.

## Persistent volumes and ownership

Node writes three named volumes:

- `sportmassage_blog_content` at `/app/content/blog` for source JSON and uploaded media.
- `sportmassage_blogger_state` at `/app/.blogger-state` for sessions, audit records, locks, and transaction recovery.
- `sportmassage_blogger_public` at `/app/.blogger-state/public` for generated releases and the atomic `current` link.

Nginx mounts only `sportmassage_blogger_public`, at `/usr/share/nginx/html:ro`. It cannot read the content source, sessions, audit records, or transaction journal.

Both images run with numeric UID/GID `10001:10001`. Named volumes created by Compose inherit that ownership from the images. If existing data is restored or bind-mounted, recursively set its numeric owner to `10001:10001`, directories to `0750`, ordinary generated/source files to `0640`, and `sessions.json` to `0600` before startup.

## Coolify variables

Configure these values as protected runtime variables on the `blogger` service:

- `BLOGGER_STUDIO_ORIGIN`: exact HTTPS origin of WF Studio.
- `BLOGGER_STUDIO_EXCHANGE_URL`: the WF Studio `/api/tool-launch/exchange` URL on that origin.
- `BLOGGER_DIRECT_PASSWORD_HASH`: supported hash generated by passing the operator-supplied password through standard input to `node scripts/generate-blogger-password-hash.mjs`.
- `BLOGGER_SESSION_SECRET`: a strong secret used only for sessions.
- `BLOGGER_HANDOFF_SECRET`: a different strong secret shared only with WF Studio.

Set the password hash and every value containing `$` as **Literal** in Coolify. Otherwise Coolify may interpret part of a scrypt hash as variable interpolation. Store only the generated hash; never store the direct plaintext password in Coolify, Git, Compose, build arguments, labels, or logs.

The Compose file fixes `HOST=0.0.0.0` only inside the isolated Blogger container. Running Node outside Compose keeps the secure default `127.0.0.1`. Umami remains disabled unless its UUID and collector URL are verified and `UMAMI_PRODUCTION_VERIFIED=true` is set explicitly.

## Startup, health, and timeouts

The Blogger entrypoint creates the persistent directories, builds a complete release, and then replaces itself with Node. Node handles `SIGTERM` and `SIGINT`, stops accepting requests with `server.close()`, and forces shutdown after 30 seconds if connections do not drain.

The proxy uses writable PID, client-body, proxy, FastCGI, uWSGI, and SCGI temporary paths under `/tmp/nginx`; its public volume remains read-only. `proxy_read_timeout 910s` is longer than the server's maximum accepted build timeout of 900 seconds.

Both health checks call `/api/blogger/health`. Keep the Studio tool disabled until the Blogger and proxy containers are healthy over HTTPS.

## Backup and restore

Snapshot all three volumes from the same stopped application state. A consistent restore must follow this order:

1. Stop both services.
2. Restore **content** into `sportmassage_blog_content`.
3. Restore private **state** into `sportmassage_blogger_state`.
4. Restore the generated **public** release volume into `sportmassage_blogger_public`.
5. Reapply UID/GID `10001:10001` and the modes documented above.
6. Start `blogger`, wait for its health check, then start `proxy`.

If the public volume is unavailable but content and private state are consistent, leave the public volume empty and let Blogger rebuild it before starting the proxy. Never restore public output from a different snapshot than its source content and transaction state.

## Activation checks

Before switching DNS or enabling the Studio tool:

1. Confirm `/`, `/blog/`, and `/admin/blogger/` load from the same HTTPS origin.
2. Confirm direct login, logout, remembered login after a Blogger restart, and Studio handoff.
3. Create and publish a disposable post, verify its public URL, and remove it.
4. Redeploy both images and confirm source, media, sessions, audit data, and the active release survive.
5. Perform one full backup and restore test using the ordered procedure above.

Do not activate the Studio integration if any check fails.
