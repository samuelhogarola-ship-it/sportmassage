# Coolify deployment for Sport Massage Blogger

This package runs the generated public website and the independent Blogger editor on one origin. Nginx is the only exposed process on container port `8080`; the Node editor stays bound to loopback on port `8787`.

## Coolify resource

Create a Docker Compose resource from this repository and select `compose.yaml`. Attach the production domain `https://sportmassagefuengirola.com` to container port `8080`. The Compose file exposes that port only to Coolify's internal proxy network; it does not publish a host port. Do not expose port `8787`.

On a VPS without Coolify, connect the existing TLS reverse proxy to the Compose network and route the domain to `sportmassage:8080`. Prefer that internal route to adding a public host-port mapping.

The Compose file creates two named persistent volumes:

- `sportmassage_blog_content` at `/app/content/blog` stores post JSON and uploaded media.
- `sportmassage_blogger_state` at `/app/.blogger-state` stores releases, sessions, audit records, locks, and transaction recovery data.

Both volumes are required. Back them up together before upgrades or restores. Never mount over all of `/app`, because application code must continue to come from the immutable image.

## Required environment variables

Configure these as protected runtime variables in Coolify. Do not put their values in Git, build arguments, Docker labels, or deployment logs.

- `BLOGGER_STUDIO_ORIGIN`: exact HTTPS origin of WF Studio.
- `BLOGGER_STUDIO_EXCHANGE_URL`: the HTTPS WF Studio `/api/tool-launch/exchange` endpoint on that same origin.
- `BLOGGER_DIRECT_PASSWORD_HASH`: supported password hash generated by piping the operator-supplied password to `node scripts/generate-blogger-password-hash.mjs` in a trusted shell.
- `BLOGGER_SESSION_SECRET`: strong secret used only for Blogger sessions.
- `BLOGGER_HANDOFF_SECRET`: strong secret shared only with WF Studio for one-time handoff validation.

The direct username and public Sport Massage origin are fixed in `compose.yaml`. Keep the session and handoff secrets independent. The optional Umami variables remain disabled by default; only set `UMAMI_PRODUCTION_VERIFIED=true` after the production collector and site UUID have been verified.

## Startup and routing

At startup, the entrypoint creates the persistent directories, builds a complete static release, renders the Nginx configuration, and then starts Node and Nginx. The container exits if either process exits so Coolify can restart the complete unit.

Nginx serves the active release for `/`, `/blog/`, and `/admin/blogger/`. It proxies the login and Studio launch endpoints, `/.well-known/wf-blogger.json`, and the `/api/admin`, `/api/blogger`, `/api/posts`, and `/api/build` route families to Node on loopback.

The image health check calls `/api/blogger/health`. A healthy response requires valid runtime configuration, usable persistent storage, and an active release.

## Activation checks

Before switching DNS or enabling the Studio tool:

1. Confirm the Coolify health check is green over HTTPS.
2. Confirm `/`, `/blog/`, and `/admin/blogger/` load from the same production origin.
3. Confirm direct login, logout, remembered login after a container restart, and Studio handoff.
4. Create and publish a disposable post, verify its public URL, then remove it.
5. Confirm a new deployment preserves the post source, media, sessions, and audit data in both volumes.
6. Configure volume backups and perform one restore test.

Do not activate the Studio integration if any check fails.
